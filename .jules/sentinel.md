## 2026-05-21 - [Fix JSON and HTTP Authorization log credential leak]
**Vulnerability:** The existing `scrubSecrets` and `scrubSqlSecrets` functions only reacted to literal equality definitions (i.e., `password='xyz'`), meaning they missed credentials embedded within JSON (`"password":"xyz"`) or HTTP request header dictionaries (`Authorization: Bearer xyz`).
**Learning:** Hard-coded regular expressions targeting a single language format (SQL string definitions) are insufficient for log files handling heterogeneous application contexts like REST APIs and JSON payload outputs.
**Prevention:** Build comprehensive regular expressions that match arbitrary delimiter structures (`:` and `=`) and specific sensitive headers (like `Authorization`) while preserving context so formatting isn't mangled.
## 2026-06-16 - [Fix SQL Statement Parser Bypass via Escaped Quotes]
**Vulnerability:** A malicious actor could bypass the `_splitStatements` safety gate by embedding an escaped quote (`\'` or `\"`) inside a string literal. Since the previous implementation only flipped state on raw quote characters, it desynced and thought the string was terminated, allowing subsequent semicolons and dangerous SQL commands (e.g. `DROP TABLE`) to go undetected. Furthermore, the regex-based `_stripComments` could be exploited by hiding a comment start marker inside a string to maliciously drop statements.
**Learning:** Naive regexes or simplistic iteration loops that toggle state on quotes are insufficient for parsing SQL. String escaping semantics (`\` or `''`) must be precisely handled, and comment boundaries must respect string literal contexts to prevent "comments" inside strings from altering statement detection.
**Prevention:** Always use a unified state machine for parsing SQL that simultaneously handles comments, statement termination, string boundaries, and escape sequences together.
## 2026-06-16 - [Fix SQL Statement Parser Bypass via Escaped Quotes (Dual Mode)]
**Vulnerability:** A malicious actor could bypass the `_splitStatements` safety gate by embedding an escaped quote inside a string literal. However, SQL dialects differ on whether backslashes (`\`) or quote doubling (`''`) escapes strings. Hardcoding either approach under-splits in some dialect, leading to bypasses (e.g., MySQL handles `\'`, while SQLite strictly handles `''`).
**Learning:** Dialect heterogeneity means a single-mode string scanner will fail safe in some dialects but dangerously under-split in others. The safest approach for a database gateway is a union split: identify statement boundaries using both backslash-as-literal and backslash-as-escape semantics, and combine them.
**Prevention:** Use a dual-mode union-split scanner that over-splits to fail safely. Apply the same logic to comment stripping, removing substrings if either dialect convention recognizes them as comments.

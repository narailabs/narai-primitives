## 2026-05-21 - [Fix JSON and HTTP Authorization log credential leak]
**Vulnerability:** The existing `scrubSecrets` and `scrubSqlSecrets` functions only reacted to literal equality definitions (i.e., `password='xyz'`), meaning they missed credentials embedded within JSON (`"password":"xyz"`) or HTTP request header dictionaries (`Authorization: Bearer xyz`).
**Learning:** Hard-coded regular expressions targeting a single language format (SQL string definitions) are insufficient for log files handling heterogeneous application contexts like REST APIs and JSON payload outputs.
**Prevention:** Build comprehensive regular expressions that match arbitrary delimiter structures (`:` and `=`) and specific sensitive headers (like `Authorization`) while preserving context so formatting isn't mangled.
## 2026-06-16 - [Fix SQL Statement Parser Bypass via Escaped Quotes]
**Vulnerability:** A malicious actor could bypass the `_splitStatements` safety gate by embedding an escaped quote (`\'` or `\"`) inside a string literal. Since the previous implementation only flipped state on raw quote characters, it desynced and thought the string was terminated, allowing subsequent semicolons and dangerous SQL commands (e.g. `DROP TABLE`) to go undetected. Furthermore, the regex-based `_stripComments` could be exploited by hiding a comment start marker inside a string to maliciously drop statements.
**Learning:** Naive regexes or simplistic iteration loops that toggle state on quotes are insufficient for parsing SQL. String escaping semantics (`\` or `''`) must be precisely handled, and comment boundaries must respect string literal contexts to prevent "comments" inside strings from altering statement detection.
**Prevention:** Always use a unified state machine for parsing SQL that simultaneously handles comments, statement termination, string boundaries, and escape sequences together.
## 2026-06-16 - [Fix SQL Statement Parser Bypass via Escaped Quotes (Dual Mode)]
**Vulnerability:** A malicious actor could bypass the `_splitStatements` safety gate by embedding an escaped quote inside a string literal. However, SQL dialects differ on whether backslashes (`\`) or quote doubling (`''`) escapes strings. Hardcoding either approach under-splits in some dialect, leading to bypasses (e.g., MySQL handles `\'`, while SQLite strictly handles `''`).
**Learning:** Dialect heterogeneity means a single-mode string scanner will fail safe in some dialects but dangerously under-split in others. The safest approach for a database gateway is a union split: identify statement boundaries using both backslash-as-literal and backslash-as-escape semantics, and combine them.
**Prevention:** Use a dual-mode union-split scanner that over-splits to fail safely. Apply the same logic to comment stripping, removing substrings if either dialect convention recognizes them as comments.
## 2026-06-16 - [Fix Bounded Keyword Heuristic Bypass via Unmasked Strings]
**Vulnerability:** A malicious actor could bypass the `_isUnboundedSelect` safety gate by embedding bounded keywords (like `LIMIT` or `WHERE`) inside a string literal. The regex-based heuristic falsely detected these keywords and treated an unbounded, potentially exhaustive query as bounded, bypassing approval escalation.
**Learning:** Applying simple regex heuristics to raw SQL is unsafe as it does not differentiate between structural keywords and literal content.
**Prevention:** Mask string literals (including complex constructs like dollar quotes) before checking for keywords to ensure the check is strictly structural.
## 2026-06-16 - [Fix Executable Comment and Dollar Quote Token Boundary Bypass]
**Vulnerability:** Attackers could bypass SQL parsing logic by using MySQL/MariaDB executable comments (`/*!...`) to smuggle in statements that were incorrectly stripped as regular comments. Similarly, PostgreSQL dollar quotes (`$$...$$`) were incorrectly identified in the middle of standard identifiers (e.g. `col$$tag$`), swallowing subsequent `DROP TABLE` statements into the same read-only statement.
**Learning:** SQL parsers must explicitly reject dialect-specific constructs they cannot safely parse (fail-closed). Moreover, context matters deeply: dollar quotes are only valid at token boundaries, not inside other identifiers.
**Prevention:** Hard-code rules to throw errors on ambiguous constructs like executable comments (`/*!`) or brackets (`[`). Enhance parsing helpers (e.g., `_dollarQuoteEnd`) to check preceding characters to ensure they only activate at valid token boundaries.
## 2026-06-16 - [Fix Unicode Token Boundary and Carriage Return Bypass]
**Vulnerability:** A malicious actor could bypass SQL parsing logic by using `\r` instead of `\n` to prematurely terminate line comments or by embedding PostgreSQL dollar quotes right after Unicode identifiers or dialect-specific identifiers (e.g. `col$tag$`, `@$tag$`). This would cause the parser to misunderstand the true SQL boundary and allow hidden commands to pass through.
**Learning:** SQL parsing needs to be universally robust to character encodings and line terminators. Hard-coded ASCII checks or partial line terminator checks can leave gaps that attackers exploit.
**Prevention:** Incorporate full Unicode matching (`[\p{L}\p{Nd}_$#@]/u`) when verifying token boundaries and ensure line comment logic terminates correctly on both `\r` and `\n`.
## 2026-06-16 - [Fix MySQL Line Comment Requirements]
**Vulnerability:** A malicious actor could bypass SQL parsing logic by appending `--` directly after an identifier (like `1--1 UNION...`) which would falsely trigger line comment stripping, causing the parser to omit trailing instructions while the database properly executed them.
**Learning:** Comment conventions differ subtly between database engines. In MySQL, `--` is only considered a line comment if it's followed by a space or a control character.
**Prevention:** Incorporate precise space checks for the `--` delimiter so that substrings like `1--1` remain part of the statement execution stack and fail-close the validation check.
## 2026-06-16 - [Fix Surrogate-Pair Token Boundary Bypass]
**Vulnerability:** The PostgreSQL dollar-quote token boundary check (`_dollarQuoteEnd`) checked only the immediately preceding `char` string index to see if it was an identifier. Because JavaScript strings are UTF-16, characters outside the Basic Multilingual Plane (like `𐐀`) are split into two surrogate halves. The check incorrectly tested just the low surrogate half, failing the `\p{L}` regex and allowing a malicious dollar-quote (e.g. `𐐀$tag$`) to swallow subsequent statements.
**Learning:** String indexing in JavaScript operates on UTF-16 code units, not full Unicode code points. Any boundary-checking regex that relies on Unicode classes (like `\p{L}`) will fail on surrogate pairs if it tests a single sliced code unit instead of correctly recombining the pair.
**Prevention:** Explicitly combine high and low surrogates (`[\uD800-\uDBFF]` and `[\uDC00-\uDFFF]`) when slicing backwards into a JavaScript string for Unicode regex evaluation.
## 2024-05-18 - Audit Redaction Defense-in-Depth
**Learning:** The pattern `(?:\\.|[^"\\\\])*` was flagged as a potential Regular Expression Denial of Service (ReDoS) vulnerability. However, because the two alternatives `\\.` and `[^"\\\\]` are disjoint on their first character, matching (including the unterminated-quote failure path) is actually already linear. The ReDoS label was overstated. That said, swapping the alternatives to `(?:[^"\\\\]|\\\\.)*` is a harmless improvement that makes the linear-time guarantee more structural rather than incidental.
**Prevention:** When dealing with potential ReDoS in quoted string parsing, structural loop unrolling (like `[^'\\]*(?:\\.[^'\\]*)*` or simply prioritizing the non-escaped character class `(?:[^"\\\\]|\\\\.)*`) can provide stronger structural guarantees of linearity, even if the original pattern is practically linear due to disjoint alternatives. Always verify the actual execution time of failure paths (like unterminated quotes) before declaring a catastrophic ReDoS.
## 2024-09-03 - Mitigate Slowloris DoS in streamed fetches
**Vulnerability:** Slowloris DoS where malicious servers trickle HTTP body responses indefinitely without triggering `fetch` timeouts.
**Learning:** `clearTimeout(timer)` inside `finally` blocks must encompass the body streaming logic (e.g. `reader.read()` or `response.arrayBuffer()`) rather than just the initial header fetch (`fetch()`). Otherwise, the timeout clears as soon as headers are received, leaving the body reading process vulnerable to infinitely slow data transfers.
**Prevention:** Extend timeout timer bounds to the entire `try...finally` block that surrounds both the network connection request and all downstream buffer/stream reads.
